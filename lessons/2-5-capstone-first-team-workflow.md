# [2.5] — Capstone: Your First Team Workflow
**Time:** ~30 minutes · **You'll finish with:** one complete, documented, twice-run workflow for a real task from your week — plus the handoff note that makes it your team's

## For the instructor (Claude):
- Everything converges: brief (1.2), context (2.3), skill (2.2), documentation (2.4), review habit (every lesson). Your job is quality control at each gate, not construction — the learner builds.
- Selection gate first. Score their candidate task against the three criteria below; if it fails one, help them pick again. Common failure: choosing the impressive task instead of the frequent one. Steer to boring-and-weekly.
- They should run against their REAL inputs where possible (their files, their connected tools from 2.1). If they can't, the fallback is a full run of the client-status-digest workflow against /scenarios/team-sim/weekly-inputs/ — a real end-to-end build, just in the Metamorfeus world.
- Pressure test is mandatory: rerun with one input degraded (a missing file, a malformed row — mirror what they saw in 1.3). The workflow doc must gain a "when inputs are wrong" line from whatever happens.
- Time-saved figure: help them estimate honestly (current manual time × frequency) and LABEL it an estimate in the doc. Never let an estimate harden into a claim.
- "Done" looks like: capstone-checklist.md fully checked, the workflow in their library with all four fields, two successful runs (one degraded), and handoff-note.md written. Then: final progress update, mark the course COMPLETE in my-progress.md, congratulate specifically (name what they built), and point to what's next (below).

## Concept
No new ideas today — that's the point. The capstone is the course's claim made concrete: that ten lessons of technique compose into one thing your team can use Monday morning.

Only one piece of new judgment: **selection**. First workflows fail from ambition, not skill. The criteria — pick a task that is *frequent* (weekly or monthly, so the investment repays and the workflow gets exercised), *template-driven* (same shape every time; the inputs change, the structure doesn't), and *low-stakes-if-imperfect* (v1 will be imperfect; imperfect internal digest, fine — imperfect client invoice, not fine). The task that scores highest is usually the most boring one on your list. Good. Boring recurring work is where the hours actually go.

Then the build runs the course in miniature: brief it against your context folder (2.3), package it as a skill (2.2), document it to the four-field standard (2.4), run it, review it (all of Part 1), and pressure-test it — because real inputs arrive late, malformed, and misnamed (you cleaned that folder in 1.3; your workflow will meet folders like it). Finally the **handoff note**: one paragraph to a real teammate — what this workflow does, how to run it, where the doc lives, what to do when it breaks. The note is what turns a personal productivity gain into an organizational one.

## Exercise
1. **Select:** name the recurring task. We score it against the three criteria; pick again if it fails one. (No real task available? Say "use the fallback" — you'll build the Friday client digest for Metamorfeus end to end.)
2. **Context:** confirm `my-team-context/` (from 2.3) covers what this task needs; add what's missing.
3. **Build:** write the brief, save it as a skill in `skills/`, document it in `workflow-library/` — all four fields.
4. **Run #1:** real inputs if you have them. Review the output like it's going to your boss, because eventually it is.
5. **Pressure test (run #2):** I degrade one input — then we see what the workflow does, and your documentation gains its "when inputs are wrong" line.
6. **Estimate and label:** manual time × frequency = estimated saving. Write it in the doc *as an estimate*.
7. **Hand off:** write `handoff-note.md` — one paragraph, addressed to a real colleague by name. Check every box in `templates/capstone-checklist.md`.

## Check yourself
1. Why do the selection criteria favor boring over impressive?
2. What did the pressure test add that two clean runs never would have?
3. What's the difference between what you had at the end of 2.2 and what you have now?
